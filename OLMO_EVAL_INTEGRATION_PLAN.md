# Integrating eduLLM-Evals custom evaluations into `olmo-eval`

**Status:** planning document (read-only investigation; no code changed).
**Goal:** run the team's custom evaluations through the standard CLI
`olmo-eval run -m <checkpoint> -t <task>` (and `olmo-eval run-external` for the
online-CAT path), reusing the harness's inference, scoring, aggregation, and
S3/DB output instead of the hand-rolled `eduLLM-Evals/scripts/` pipeline.

Repo root: `/Users/cat/alpha-projects/olmo-eval-full`.

> **Execution model (2026-08-05):** these evals run **retroactively, batched over saved
> training checkpoints** on AWS (not during training) — see `AWS_CHECKPOINT_EVAL_PLAN.md` §7 and
> `tests/aws/CHECKPOINT_LAUNCHER_SCOPING.md` §3.5. This is purely *when/where* `olmo-eval run`
> is invoked; it does **not** change *what* this doc scopes — the tasks, Qwen judge, and MCQ
> CAT still need registering exactly as described below.

## 1. Summary & current state

There are **two things** to integrate:

1. **Open-response benchmarks graded by a custom Qwen LLM-judge.** TutorEval and
   TutorBench (plus siblings IFEval / InFoBench / BiGGen / Bridge / EduBench /
   WildBench) live as `scenarios.jsonl` + `rubrics*.jsonl` under
   `eduLLM-Evals/data/<Benchmark>/`. Candidate responses are generated by a
   standalone fleet runner (`eduLLM-Evals/tutor_cat/respgen/`), staged
   (`eduLLM-Evals/scripts/stage_judge_inputs.py`), graded by a **frozen Qwen3.5-9B
   judge via vLLM** (`eduLLM-Evals/aws_judge_handoff/scripts/run_judge_validation.py`,
   ingested by `eduLLM-Evals/scripts/run_judge_grading.py`), and assembled into a
   pass/fail response matrix for MIRT calibration/CAT. **None of this is wired into
   the olmo-eval harness today.**

2. **A multiple-choice (MCQ) benchmark the team ran CAT on.** See §1.1.

### What already exists in `olmo-eval` (big wins — most seams are built)

- **Task framework + registry.** `src/olmo_eval/evals/tasks/common/base.py`
  (`Task`, `TaskConfig`), `src/olmo_eval/evals/tasks/common/registry.py`
  (`@register`, `get_task`, variants). `-t <task>` resolves through `get_task`.
- **Native LLM-as-judge scorers.** `src/olmo_eval/common/scorers/llm_judge.py`
  provides `LLMJudgeScorer` (a `ContextScorer`), `RubricJudgeScorer`,
  `SimpleQAJudgeScorer`, `SafetyScorer`. A judge scorer can call **either** an
  external API (`judge_fn`, e.g. OpenAI) **or** a harness-managed auxiliary
  provider by name (`provider_name`).
- **Auxiliary/judge provider wiring in the harness.**
  `HarnessConfig.auxiliary_providers` (`src/olmo_eval/harness/config.py`) →
  started as local vLLM servers by `InferenceManager`
  (`src/olmo_eval/runners/asynq/runner.py:653-666`) → exposed as a
  `ProviderRegistry` on `ScoringContext.inference_pool`
  (`runner.py:803-821`) → resolved in a scorer via `context.get_provider(name)`
  (`src/olmo_eval/common/execution/environment.py:56-59`). **Live exemplar:**
  `harmbench:wg_judge` uses `SafetyScorer(provider_name="wg_judge", ...)`
  (`src/olmo_eval/evals/tasks/harmbench.py:133-146`).
- **Async judge scoring path.** `Task.score_responses` /
  `_apply_scorers_async` already routes `ContextScorer`s (LLM judges)
  concurrently with a per-call semaphore
  (`src/olmo_eval/evals/tasks/common/base.py:589-825`).
- **Adaptive testing / CAT is ALREADY integrated.** `src/olmo_eval/adaptive/`
  is a full 3PL-IRT + Fisher-information CAT core (`irt.py`, `cat.py`, `bank.py`,
  `benchmarks.py`). It is wired **two ways**: an **offline** post-hoc report via
  `AtlasAdaptiveMixin` (`src/olmo_eval/evals/tasks/atlas.py`, tasks
  `atlas_<name>`) and an **online, item-by-item live** CAT via
  `AtlasExternalEval` (`src/olmo_eval/evals/external/benchmarks/atlas/eval.py`,
  external evals `atlas_<name>`). Both consume a calibrated bank from
  `AdaptiveTesting/Inputs/ATLAS/<subdir>/` and key items on
  `Instance.metadata["id"]`.
- **Suites & aggregation.** `src/olmo_eval/evals/suites/registry.py`
  (`Suite`, `AggregationStrategy`, `make_suite`), consumed by
  `src/olmo_eval/runners/processing/aggregation.py`.

### What is missing

- No olmo-eval **task** for TutorEval/TutorBench (data loader + prompt builder
  from the eduLLM `scenarios.jsonl`, with multi-turn `conversation_context`).
- No **Qwen judge** auxiliary-provider preset, and no **rubric/criterion-level
  judge scorer** that reproduces the frozen `generic-binary` prompt + evidence
  gate + JSON `{verdict, evidence, rationale}` parsing.
- No olmo-eval task for the **pedagogy MCQ** benchmark.
- The team's **multidimensional (M2PL, skill q-matrix) CAT** over rubric
  criteria (`eduLLM-Evals/tutor_cat/`) has **no equivalent** in
  `src/olmo_eval/adaptive/`, which is strictly **unidimensional 3PL over whole
  items**. These are different IRT models (see §5, §6).

### Reconciliation update (2026-08-04): a standalone MCQ CAT package now exists

A teammate landed **`diagnostics/mcq_cat/`** (plan: `Plan/mcq_cat_diagnostics/README.md`), a
standalone, **offline, per-checkpoint** MCQ CAT engine that is **decoupled from `olmo_eval`**.
This is a **third** CAT implementation alongside the two this doc contrasts
(`src/olmo_eval/adaptive/` unidimensional 3PL, and `eduLLM-Evals/tutor_cat/` multidimensional
M2PL), and it updates the framing below:

- **One contract spans uni + MIRT.** `diagnostics/mcq_cat/base.py` defines a `CatStyle` ABC
  where ability/discrimination are scalars for unidimensional models and **tuples for MIRT**
  (`IRTBank.dimensions`), driven by a generic engine (`common/cat_loop.py`). So
  **multidimensional MCQ CAT is explicitly in-scope here** — but **offline and outside
  `olmo-eval run`**, as a fresh standalone engine, *not* a port into `src/olmo_eval/adaptive/`
  nor a lift of `tutor_cat/`.
- **It does not reuse olmo-eval's CAT or scoring.** It rolls its own log-likelihood MCQ scorer
  (`common/inference.py`, HF `from_pretrained`) and IRT loader (`common/irt_params.py`), driven
  by `python -m diagnostics.mcq_cat.runner` — **not** `olmo-eval run-external`/ATLAS.
  `common/benchmark_download.from_olmo_eval_task` is a **stub extension point** if a style later
  wants to source items from an olmo-eval MCQ task (`src/olmo_eval/evals/tasks`).
- **Impact on the phases below.** Phase 4/5 (add a `pedagogy` olmo-eval task, then reuse
  olmo-eval's unidimensional ATLAS CAT) is now **one of two possible homes** for MCQ CAT.
  **Decision needed (open question):** is MCQ/pedagogy CAT delivered as an **offline
  `diagnostics/mcq_cat/` style**, as **live olmo-eval `run-external` ATLAS CAT**, or both? The
  "keep multidimensional CAT offline" guidance (§5.4, §6) still holds — the new package **is**
  that offline home, just built fresh rather than ported from `tutor_cat`. Styles are not yet
  implemented (`diagnostics/mcq_cat/styles/` is currently empty); the scaffolding is frozen.

### 1.1 Which benchmark is "the MCQ one"?

**Conclusion: the custom MCQ benchmark the team ran CAT on is the Pedagogy
Benchmark — `AI-for-Education/pedagogy-benchmark`.**

Evidence:

- The only committed MCQ CAT run artifact,
  `eduLLM-Evals/mcq_runs/run_20260724_211626_mcq/manifest.json`, records
  `"pipeline": "mcq_calibration"`, `"prompt_version": "mcq-answer-v1"`,
  `"dataset_hf_id": "AI-for-Education/pedagogy-benchmark"`,
  `"dataset_path": "data/pedagogy_benchmark.jsonl"`, 25 items × 24 models.
- The pre-registration design
  (`eduLLM-Evals/plans+prds/200-Model Run - Pre-Registration + Design.md`, §4.1)
  explicitly classes the MCQ benchmarks as **unidimensional** and names them
  "**openbookqa, socialiqa, piqa, pedagogy**", with a per-(benchmark,model)
  output schema `Outputs/mcq/<bench>/<org__model>.csv = correct|wrong` — exactly
  the grid consumed by the unidimensional 2PL/CAT pipeline
  `eduLLM-Evals/tutor_cat/mcq_irt/` (`matrix.py` reads
  `question_id,model,result` CSVs; `pipeline.py`/`cat.py` calibrate 2PL + run a
  Fisher CAT).

Nuance worth stating plainly: `tutor_cat/mcq_irt/pipeline.py` also lists
`DEFAULT_BENCHMARKS = ["arc_challenge","arc_easy","openbookqa","sciq"]`, but
those are standard MCQ item banks used as **IRT-recovery validation**, and
`arc_challenge / piqa / socialiqa / sciq / csqa / hellaswag / winogrande` **already
exist as olmo-eval tasks** (and arc/hellaswag/winogrande/csqa/piqa already have
ATLAS CAT wiring). So the only **custom** MCQ benchmark that needs a new
olmo-eval task is **pedagogy** (`openbookqa` also has no olmo-eval task yet, but
it is not the team's custom benchmark). See "Assumptions" at the end.

## 2. Target architecture

### (a) TutorEval / TutorBench as olmo-eval task(s)

Add a task module (e.g. `src/olmo_eval/evals/tasks/tutorbench.py`, and a
`tutoreval.py`) with a shared base class that:

- **Data loading.** Points `TaskConfig.data_source` at the eduLLM
  `scenarios.jsonl` (via `hf://` if uploaded, or a local/S3 `DataSource`).
  Implements `process_doc(doc, index)` mapping the eduLLM `Scenario` schema
  (`scenario_id`, `prompt`, `conversation_context`, `reference_solution`,
  `criterion_ids`, `subject`, `use_case`, optional per-instance `system_prompt`)
  to an `Instance`. Store `scenario_id` in `metadata["id"]` (bank/CAT join key),
  and carry the criteria/rubrics either inline in `metadata` or loaded from the
  paired `rubrics*.jsonl`. Cite formats:
  `eduLLM-Evals/tutor_cat/schemas.py` (`Scenario`, `Rubric`) and the sampled
  `data/TutorBench/scenarios.jsonl` / `rubrics_qmatrix_final.jsonl`.
- **Prompt building.** `format_request` produces a `RequestType.CHAT` request.
  Multi-turn scenarios must replay `conversation_context` (list of
  `{role, content}`, roles `student`/`tutor`) as prior messages, then the final
  `prompt`, mirroring `tutor_cat/judge.build_messages` and the respgen tutor
  prompt (`tutor_cat/respgen/prompts.py`). Use a `ChatFormatter`
  (`src/olmo_eval/common/formatters.py`) or a small custom formatter.
- **Scoring.** Attach the rubric-judge scorer from (b). Because one scenario has
  **many criteria**, this is the main schema-fit decision (see §5/§6): either
  one judge call per criterion (matches the eduLLM semantics) with the criterion
  set carried on the instance, or a single multi-criterion call.

### (b) Qwen judge as an auxiliary provider + a rubric/criterion judge scorer

Two pieces:

1. **Auxiliary provider preset.** Add a harness preset (or extend an existing
   one in `src/olmo_eval/harness/presets.py`) whose `auxiliary_providers`
   contains a `"qwen_judge"` entry:
   `ProviderConfig(kind=VLLM_SERVER, model="Qwen/Qwen3.5-9B",
   revision="c202236235762e1c871ad0ccb60c8ee5ba337b9a", ...)`
   (identity from `eduLLM-Evals/judge_frozen.yaml`). This is the exact seam the
   runner already knows how to start (`runner.py:653-666` →
   `InferenceManager` → `ProviderRegistry`), co-resident on auxiliary GPUs via
   `gpu_planner.get_auxiliary_gpus()`. The judge could alternatively be an
   external OpenAI-compatible endpoint via `judge_fn` (see §5).
2. **`RubricCriterionJudgeScorer`.** A new `LLMJudgeScorer` subclass
   (`src/olmo_eval/common/scorers/`) with `provider_name="qwen_judge"`.
   - `format_judge_prompt` reproduces the frozen **`generic-binary`** prompt:
     the evidence-gated decision policy + `<instruction>/<candidate_response>/
     <criterion>/<reference_background>` blocks (source:
     `aws_judge_handoff/scripts/run_judge_validation.py:942-969` and
     `EVIDENCE_DECISION_POLICY` at lines 46-53).
   - `parse_judge_response` parses the strict JSON `{verdict, rationale,
     evidence}`, maps `verdict=="pass"→1.0` else `0.0`, and treats
     unparseable / `no_decision` as fail (or MISSING/NaN, see §5) — mirroring
     `run_judge_validation.py` `normalize_verdict` / `run_judge_grading.py`
     ingest.
   - Persists the raw verdict + evidence into `output.metadata` /
     `instance.metadata` (as `SafetyScorer` does with `judge_result`) so the
     downstream CAT/report can read pass/fail per criterion.

   Reuse `RubricJudgeScorer` (`llm_judge.py:398-467`) as the structural
   template; the criterion text becomes the rubric, and the score pattern is
   replaced by JSON-verdict parsing.

### (c) The pedagogy MCQ benchmark as an olmo-eval task

Add `src/olmo_eval/evals/tasks/pedagogy.py` modeled on the existing MCQ tasks
(`arc.py`, `piqa.py`, `csqa.py`, `sciq.py`): `process_doc` maps the
`pedagogy-benchmark` question/choices/answer to an `Instance` with
`metadata["id"]` (stable question id) and `metadata["gold_idx"]`, a loglik/MC
formatter, and an accuracy metric whose `compute_instance` returns 0/1. This
directly satisfies both the standard MCQ path **and** the ATLAS CAT contract
(the CAT reads a 0/1 primary-metric cell keyed on `metadata["id"]`).

### (d) CAT hooked in

The MCQ CAT path is essentially **free** once (c) exists, because olmo-eval's
CAT is generic over "any task whose primary metric yields a 0/1 cell keyed on
`metadata["id"]`":

- **Offline report:** register `atlas_pedagogy` by combining
  `AtlasAdaptiveMixin` with the pedagogy task (pattern:
  `src/olmo_eval/evals/tasks/atlas.py:189-212`), pointing at a calibrated
  pedagogy bank subdir under `AdaptiveTesting/Inputs/ATLAS/`.
- **Online live CAT:** add `AtlasBenchmark("pedagogy", "pedagogy", "pedagogy",
  scoring=SCORING_MCQ_LOGLIK, ...)` to `_BENCHMARKS` in
  `src/olmo_eval/adaptive/benchmarks.py`; the online external eval
  `atlas_pedagogy` is then generated automatically
  (`external/benchmarks/atlas/eval.py:231-237`).

The **open-response multidimensional CAT** (TutorBench skill θ over rubric
criteria) does **not** map onto the current unidimensional 3PL core and is
proposed as out-of-scope for phase 1 (see §5, §6, §4-Phase 6).

> **Reconciliation (2026-08-04):** MCQ CAT may instead be delivered **offline** via the new
> standalone `diagnostics/mcq_cat/` package (one `CatStyle` contract spanning uni **and** MIRT),
> which is decoupled from this ATLAS path. Whether pedagogy MCQ CAT lives in that package, in
> live olmo-eval `run-external` ATLAS CAT, or both, is an open decision — see the
> "Reconciliation update" note in §1.

## 4. Phased step list

Phases 1–4 are **largely independent** and can be parallelized; the judge-scorer
(Phase 3) depends on the judge provider (Phase 2); the MCQ-CAT (Phase 5) depends
on the MCQ task (Phase 4). Phase 6 is optional/research.

- **Phase 1 — TutorEval/TutorBench task with a stub scorer (independent).**
  Add the task module + `process_doc` + multi-turn `format_request`; register
  with `@register("tutorbench")` / `@register("tutoreval")`. Use a trivial
  placeholder metric so `olmo-eval run -m <ckpt> -t tutorbench` produces
  responses end-to-end (generation + I/O + S3) with no judge yet. Validates data
  loading, prompt shape, and the run/output plumbing.

- **Phase 2 — Wire the Qwen judge provider (independent).**
  Add a `qwen_judge` auxiliary provider preset (Qwen3.5-9B, pinned revision from
  `judge_frozen.yaml`) and confirm the runner starts it and it appears in
  `ProviderRegistry.names`. Smoke-test via the existing `harmbench:wg_judge`
  mechanism to be sure aux-GPU planning and the provider lookup work.

- **Phase 3 — Rubric/criterion judge scorer (depends on Phase 2; can co-dev
  with Phase 1).** Implement `RubricCriterionJudgeScorer(provider_name="qwen_judge")`
  reproducing the `generic-binary` prompt + evidence gate + JSON verdict parse.
  Swap it in for the Phase 1 stub. Decide per-criterion fan-out (see §5). Verify
  pass/fail matches the frozen runner on a handful of cached cases from
  `staging/`/`aws_judge_handoff/inputs/judge_cases.blinded.jsonl`.

- **Phase 4 — Pedagogy MCQ task (independent).**
  Add `pedagogy.py` (MCQ loglik-argmax + accuracy metric, `metadata["id"]` +
  `gold_idx`). `olmo-eval run -m <ckpt> -t pedagogy` gives standard accuracy.

- **Phase 5 — CAT hookup for pedagogy (depends on Phase 4).**
  Produce a calibrated pedagogy 3PL bank in ATLAS CSV format
  (`AdaptiveTesting/Inputs/ATLAS/pedagogy/`), add the `AtlasBenchmark("pedagogy",
  ...)` row, register `atlas_pedagogy` offline task + online external eval. Run
  `olmo-eval run -t atlas_pedagogy` (offline report) and
  `olmo-eval run-external ... atlas_pedagogy` (live CAT).

- **Phase 6 — (Optional/research) Multidimensional open-response CAT.**
  Only if the team wants the TutorBench **skill-θ CAT** inside `olmo-eval run`.
  Requires porting the M2PL engine (`tutor_cat/mirt.py`, `selector.py`,
  `engine.py`) as a new multidimensional adaptive module, plus shipping the
  fitted `rubrics_qmatrix_*` bank. High effort; recommend keeping this as an
  **offline post-processing harness** over olmo-eval judge outputs unless there
  is a strong reason to make item selection live.

## 5. Key design decisions / open questions

1. **Judge co-resident vs separate endpoint.** The harness supports both:
   `provider_name="qwen_judge"` starts Qwen3.5-9B on auxiliary GPUs alongside the
   checkpoint (needs GPU budget; `gpu_planner.get_auxiliary_gpus()`), while
   `judge_fn` targets an external OpenAI-compatible endpoint (the frozen runner
   already speaks this via `tutor_cat/judge.OpenAICompatibleJudge` and
   `judge_frozen.yaml.base_url`). Decision needed: co-resident (self-contained,
   GPU-hungry) vs external endpoint (matches current AWS handoff, needs a
   reachable server + `JUDGE_API_KEY`).

2. **Per-criterion fan-out vs per-scenario call.** The eduLLM semantics are
   **one judge call per criterion** (`stage_judge_inputs.py` emits one row per
   model×scenario×criterion; `engine.py` grades each `rubrics_for(sid)`). The
   olmo-eval scorer scores per `(instance, output)`. Options: (a) one `Instance`
   per criterion (clean per-call mapping, but N× instances and duplicated
   generations unless responses are shared), or (b) one `Instance` per scenario
   with the scorer looping criteria internally and emitting a per-criterion
   verdict map. (b) better matches "one response, many criteria" and avoids
   regenerating; it needs the scorer to aggregate to a scenario score while
   persisting per-criterion cells for any downstream CAT.

3. **`no_decision` / unscorable handling.** The frozen calibration path maps
   VOID/unscorable to **MISSING (NaN)** for MIRT (`run_judge_grading.py`
   `--no-decision-policy missing`), whereas olmo-eval scorers return a float and
   the `ContextScorer` error path defaults to `0.0`. Decide whether
   olmo-eval-side scoring should treat unscorable as fail (0.0) or record NaN and
   exclude — this changes reported accuracy and any IRT cell.

4. **Where does CAT belong?** For **MCQ/pedagogy**, live CAT inside
   `olmo-eval run-external` is a clean fit (unidimensional 3PL already built). For
   **open-response multidimensional** TutorBench, keep CAT **offline** (post-hoc
   over the full judged matrix) unless Phase 6 is funded — the current
   `src/olmo_eval/adaptive/` cannot represent skill vectors / q-matrices.

5. **Item-bank shipping.** ATLAS banks are "supplied out of band (synced from S3
   to local disk at run time)" and joined on `metadata["id"]`
   (`adaptive/bank.py`, `evals/tasks/atlas.py:118-138`). Need to decide how the
   pedagogy 3PL bank (and, if Phase 6, the rubric q-matrix bank) is produced,
   versioned, and shipped to `AdaptiveTesting/Inputs/ATLAS/`.

6. **Data hosting.** eduLLM data is local `data/<Benchmark>/*.jsonl`. Decide
   whether to load via a local/S3 `DataSource` or upload to HF (`hf://...`) as
   most existing tasks do; the `Scenario.source` field is already a HF URL for
   some banks.

7. **Judge determinism / provenance.** The frozen judge pins temperature 0,
   seed 42, a specific HF revision, and stamps prompt/normalization/evidence
   policy versions on every row (`judge_frozen.yaml`,
   `run_judge_grading.py:PROVENANCE_FIELDS`). If calibration parity matters,
   the olmo-eval scorer must pin the same and record provenance in output
   metadata.

## 6. Risks

- **The two CAT systems are different IRT models.** olmo-eval =
  **unidimensional 3PL** over whole items (`adaptive/irt.py`); eduLLM =
  **multidimensional M2PL** with a per-criterion skill **q-matrix**
  (`tutor_cat/mirt.py`, `schemas.Rubric.q/a/b`). The MCQ path maps cleanly; the
  open-response skill-θ CAT does **not**. Do not conflate them.
- **Multi-stage judge staging logic.** The current pipeline is not "grade a
  response" — it is validate → stage (auto-fail policy for
  error/empty/missing/degenerate cells, `stage_judge_inputs.py`) → blind →
  grade (frozen runner) → ingest/normalize → assemble matrix. An olmo-eval
  scorer collapses this into one call; the **auto-fail rules** (empty/errored
  outputs scored 0 without a judge call) and **blinding** must be reproduced or
  deliberately dropped, or scores will diverge from the frozen results.
- **Per-criterion fan-out cost.** TutorBench has ~10 criteria/scenario and
  thousands of criteria total (the pre-reg cites a 6,845-criterion bank); at
  1 judge call/criterion this is a large auxiliary-inference load. Concurrency is
  bounded by `scoring_concurrency`, but GPU budget for a co-resident 9B judge is
  a real planning constraint.
- **CAT needs a fitted bank not available at run time.** Both CAT paths require a
  **pre-calibrated** bank; live pedagogy CAT is only meaningful with a fitted 3PL
  bank keyed to the exact question ids the task emits. Missing/misaligned banks
  degrade gracefully (offline mixin logs a warning and skips; online returns an
  error result), so a wiring mistake yields "no CAT report" rather than a crash —
  but also silently no adaptive result.
- **Positional-id / id-bridge alignment.** The ATLAS bank join keys on
  `metadata["id"]`; if pedagogy ids are positional, the bridge must be built
  against olmo-eval's exact split ordering or the join finds zero overlap
  (`benchmarks.py:56-64`, `atlas.py:128-138`).
- **Calibration parity of scoring.** For any transferred IRT bank, the online/
  offline 0/1 cell must be produced by the **same** scoring rule the bank was
  calibrated under (the code repeatedly flags this for gsm8k/math). A judge
  prompt/threshold drift silently shifts item difficulty/θ.
- **Schema coverage.** eduLLM `Scenario`s carry multi-turn context, per-instance
  system prompts, reference solutions, subjects/use-cases, and modality (some
  non-text, filtered today). The task loader must handle all of these or filter
  consistently with the eduLLM loader (`benchmarks.yaml` is text-only).
